## Debate Topic: Daemon Port Discovery for Worktree Heartbeat System

### Context

A developer tool manages git worktrees. When a worktree IDE window is opened, a background task inside that window sends HTTP POST requests every 5 seconds to a daemon running on localhost, telling the daemon "I'm still alive." When the IDE window is closed, the terminal running that task is destroyed, the POST requests stop, and the daemon — having received no heartbeat for 15 seconds — concludes the window was closed and triggers cleanup.

The daemon listens on a dynamic port assigned by the OS (port 0, to avoid conflicts). That port number must be baked into the curl command inside the worktree's `.vscode/tasks.json` at generation time. If the daemon was started by a previous invocation, the current invocation needs to discover what port the daemon is listening on so it can write the correct curl URL into the new worktree's tasks.json.

**Constraint:** The solution must NOT write the port to a file inside the repository.

The daemon and CLI are written in TypeScript/Node.js. Primary platform is macOS, secondary is Linux.

### Your Task

Argue for the BEST approach to solve this port discovery problem. Consider and evaluate these categories:

1. **Unix Domain Socket** — Daemon listens on a well-known socket path (e.g., `$TMPDIR/worktree-daemon.sock`). New invocations connect to the socket and query for the TCP port. Eliminates port discovery if used as primary transport.

2. **Port file outside the repo** — Write `{ pid, port, startedAt }` to a well-known path like `os.tmpdir()/worktree-daemon/daemon.json`. Validate staleness via PID check and port probe.

3. **Hash-based deterministic port** — Both daemon and client compute the same port from a hash of stable inputs (username + repo path), mapped to range 49152-65535. Increment on collision.

4. **OS process table inspection** — Use `lsof -iTCP -sTCP:LISTEN -P -n -p <PID>` to discover the port from the daemon's PID. Requires knowing the PID first.

5. **Fixed port with sequential probing** — Start at a known default port (e.g., 19876), try to bind. Client tries the same sequence. Identity verified via health endpoint.

6. **Any other approach you think is superior.**

### Evaluation Criteria

For each approach, evaluate:
- **Implementation complexity** (lines of code, dependencies)
- **Reliability** (crash recovery, stale state, race conditions)
- **Cross-platform support** (macOS + Linux)
- **Multi-daemon support** (multiple repos with independent daemons)
- **Security** (localhost binding, no unintended exposure)
- **Developer experience** (debuggability, transparency)
- **Industry precedent** (what do similar tools do?)

### Deliverable

1. Rank all approaches from best to worst with justification.
2. Identify the single best approach and explain why.
3. Identify any hybrid approaches that combine the strengths of multiple options.
4. Flag any pitfalls or edge cases that the implementer must handle.

Because the endpoint is only injected when [`writeWorktreeTasksFile`](file:///Users/matkatmusicllc/Programming/worktree-spawn-util/src/ide/index.ts#L123) runs, and the daemon transport is still unconstrained in [`src/cli/daemon.ts`](file:///Users/matkatmusicllc/Programming/worktree-spawn-util/src/cli/daemon.ts#L1), this is the right time to remove the discovery problem instead of engineering around it.

**Ranking**
1. `Other`: replace raw `curl` with a `worktree-spawn-util heartbeat` CLI subcommand that talks to the daemon over a per-repo Unix domain socket.
Complexity is still modest in Node, reliability is highest because discovery disappears, macOS/Linux support is excellent, multi-daemon support is clean with repo-hash socket names, security is best because there is no TCP listener to expose, DX is good because the protocol stays internal, and precedent is strong: local control daemons commonly use Unix sockets or pipes.

2. Unix domain socket as the primary transport, still using HTTP and `curl --unix-socket`.
This is nearly as good as `#1`. Complexity is low to moderate, reliability is high, cross-platform is good for your stated targets, and security is strong. I rank it slightly lower only because it depends on shell quoting and `curl` feature availability instead of your own CLI.

3. Port file outside the repo.
This is the best TCP-compatible fallback. Complexity is low, portability is excellent, DX is transparent, and multi-daemon support is easy with one file per repo. The downside is reliability: you now have stale-file handling, atomic writes, PID reuse, and race windows. Security is acceptable if the daemon binds only to `127.0.0.1` and the file is user-private.

4. Fixed port with sequential probing.
This can work, but it is a brute-force discovery scheme. Complexity is moderate, portability is fine, and debugging is simple enough, but reliability degrades as daemon count grows. You need a bounded port range, strict daemon identity checks on `/health`, and careful concurrent-start handling. Precedent exists for single-instance dev servers, not for multi-daemon local control planes.

5. Hash-based deterministic port.
It looks elegant and usually isn’t. Complexity becomes deceptive because collision resolution, realpath normalization, and split-brain startup logic turn into a custom discovery protocol anyway. Reliability is worse than `#4`, DX is worse, and industry precedent is weak.

6. OS process table inspection.
This is the worst runtime design. It requires a PID source first, depends on external tooling like `lsof`, is race-prone around restarts, and is more appropriate for manual debugging than product behavior. Cross-platform support is weaker than the other options and the implementation becomes shell-parse glue.

**Single Best Approach**
Use a per-repo Unix domain socket as the primary control channel, and have the VS Code task call your own CLI subcommand instead of embedding a raw TCP URL.

That means the generated task becomes something like `worktree-spawn-util heartbeat --repo-root <abs> --worktree <name>`, and the CLI computes the socket path from `realpath(repoRoot)`. No port discovery, no repo file, no localhost exposure, no `curl` dependency, and an easy future path to Windows named pipes if you ever need it.

**Best Hybrids**
- Best practical hybrid: UDS for control and heartbeats, optional TCP only for ad hoc debugging.
- If you must keep TCP heartbeats: use a well-known UDS control socket to ask the daemon for its current TCP port.
- If you must keep TCP and cannot add UDS: use the outside-repo port file, not deterministic ports or process inspection.

**Pitfalls**
- Canonicalize the repo root with `realpath()` before deriving any socket name.
- Keep socket paths short; Unix socket path limits are tight on macOS and Linux.
- Put sockets in a user-private runtime dir with `0700` permissions.
- On startup, if the socket path already exists, try connecting before unlinking it; only remove it after a failed probe.
- If you use any state file fallback, write atomically and include more than PID alone.
- If any TCP listener remains, bind explicitly to `127.0.0.1`, not `0.0.0.0` or wildcard IPv6.
