## Research Task: Daemon Port Discovery for Worktree Heartbeat System

### Context

A developer tool manages git worktrees. The architecture:

1. A CLI (`pick-repo.ts`) creates a git worktree and generates a `.vscode/tasks.json` file
2. When the IDE opens the worktree, a background task runs a curl command every 5 seconds: `curl -X POST http://localhost:<PORT>/heartbeat/<worktree-name>`
3. A daemon process receives these heartbeats. If no heartbeat arrives for 15 seconds, the daemon concludes the IDE window was closed and triggers cleanup (deleting the worktree, killing tmux sessions, etc.)
4. The daemon listens on a dynamic port (port 0) assigned by the OS to avoid conflicts
5. The port must be known at tasks.json generation time so the curl URL is correct

**The Problem:** If the daemon was already started by a previous `pick-repo.ts` invocation, a new invocation needs to discover the daemon's port to write the correct curl URL into the new worktree's tasks.json.

**Constraint:** The solution must NOT write the port to a file inside the git repository.

**Stack:** TypeScript/Node.js. Primary platform: macOS. Secondary: Linux.

### Research Questions

1. What are ALL viable approaches to share a dynamically assigned port between independent process invocations without a file in the repo?

2. For each approach, evaluate:
   - Implementation complexity (lines of code, dependencies needed)
   - Reliability (crash recovery, stale state handling, race conditions)
   - Cross-platform support (macOS + Linux)
   - Multi-daemon support (multiple repos with independent daemons running simultaneously)
   - Security (localhost binding, no unintended network exposure)
   - Developer experience (debuggability, transparency, ease of troubleshooting)
   - Industry precedent (what do similar tools like tmux, Docker, Chrome DevTools, PostgreSQL do?)

3. What is the single best approach and why?

4. Are there hybrid approaches that combine strengths of multiple options?

5. What pitfalls and edge cases must the implementer handle?

### Approaches to Consider (non-exhaustive)

- Unix domain socket at a well-known path
- Port/PID file outside the repo (tmpdir, ~/.config, XDG dirs)
- Hash-based deterministic port derivation
- OS process table inspection (lsof/ss)
- Fixed port with sequential probing
- Process argument inspection (ps)
- Any other approach you think is viable

codex
The best design for this repo is to stop solving “port discovery” at all: make the heartbeat daemon speak HTTP over a Unix domain socket, and have the generated task use `curl --unix-socket ... http://localhost/heartbeat/<worktree>`. In this codebase, that is a low-cost change because task generation is centralized in [src/ide/index.ts:123](/Users/matkatmusicllc/Programming/worktree-spawn-util/src/ide/index.ts#L123) and the daemon is still a stub in [src/cli/daemon.ts:1](/Users/matkatmusicllc/Programming/worktree-spawn-util/src/cli/daemon.ts#L1).

**Viable Approaches**
1. Unix domain socket as the primary transport: `80-150` LoC, no deps; highest reliability because there is no dynamic port to discover; native on macOS and Linux; multi-daemon is easy with one socket per repo hash; strongest security because nothing is network-exposed; good DX with `curl`, worse for browser/Postman; strongest precedent overall: Docker, tmux, PostgreSQL, ssh-agent all rely on local sockets.
2. Port/PID state file outside the repo: `60-120` LoC, no deps if you use atomic rename; very reliable if you store `{pid, port, repoRealpath, startedAt, nonce}` and validate with `kill(pid, 0)` plus `/health`; macOS/Linux fine; multi-daemon easy with one file per repo hash; security depends on `127.0.0.1` binding and `0700` parent dir; best DX if you want plain TCP HTTP; precedent: Chrome/ChromeDriver uses `DevToolsActivePort`, PostgreSQL also writes companion lock state.
3. Unix socket as a control plane, ephemeral TCP as a data plane: `110-180` LoC; very reliable; macOS/Linux fine; multi-daemon fine; safer than pure TCP because discovery is local-only; best hybrid DX because heartbeats can stay HTTP/TCP if you want them inspectable, while discovery is deterministic.
4. Fixed port range with sequential probing plus a health endpoint: `40-90` LoC; acceptable reliability for small daemon counts, but races and accidental collisions are real; macOS/Linux fine; multi-daemon works only until the range gets crowded; security is okay if bound to `127.0.0.1`; precedent: dev servers like Vite probe the next port, but they also expose that the actual port may drift.
5. Hash-based deterministic port derivation: `30-70` LoC for the base idea, more once collision handling is honest; reliability is weaker because a collision with another app or another repo forces a fallback, which recreates discovery anyway; cross-platform fine; multi-daemon only good if collisions are rare; security same as localhost TCP; low operational transparency when the chosen port is “magic”.
6. `launchd`/`systemd` socket activation: highest reliability once installed, but `150-300+` LoC plus service manifests and install flow; not a clean single solution across macOS and Linux; multi-daemon can be good; strong precedent in OS-managed daemons, but probably too heavy for this tool.
7. Process table inspection via `lsof`/`ss`: `40-100` LoC plus shellout parsing; brittle on systems missing the expected tool or with permission quirks; cross-platform is uneven because macOS and Linux use different commands; okay as a recovery tool, not a primary design.
8. Process argument inspection via `ps`: lowest implementation cost, worst reliability; only works if you deliberately stuff the repo identity or port into args or process title, and even then parsing is brittle and stale-state handling is poor. I would treat this as debugging-only.

**Single Best Choice**
Use a per-repo Unix socket and make it the heartbeat endpoint. For this tool, the heartbeat is local-only, machine-local, and generated into `tasks.json` ahead of time. A socket path like `/tmp/wtsu-<uid>/<repoHash>.sock` is deterministic, short enough for macOS path limits, supports multiple repos cleanly, and removes the entire dynamic-port-discovery problem. If you later want a human-friendly debug endpoint, add an optional localhost TCP port and expose it through the socket.

**Best Hybrids**
- Best practical hybrid: UDS for heartbeat/control, optional TCP port for debugging or future browser-facing APIs.
- Best TCP-only hybrid: external state file outside the repo as a fast path, always validated by `/health` before use.
- Recovery hybrid: state file or socket first, `lsof`/`ss` only as a last-resort repair path.

**Pitfalls To Handle**
- Use `realpath(repoRoot)` before hashing, or symlinks will create duplicate daemon identities.
- Keep socket paths short; macOS Unix socket paths are tighter than Linux.
- On startup, if the socket path already exists, try connecting before unlinking it; only remove it when it is stale.
- Put sockets/state under a user-owned runtime dir with `0700` permissions.
- If you keep any TCP endpoint, bind to `127.0.0.1` explicitly, not `0.0.0.0`.
- If you use a state file, never trust it without PID liveness plus daemon identity validation.
- Handle concurrent `pick-repo.ts` invocations for the same repo so only one daemon wins.
- If the repo is moved on disk, the old daemon identity should not be silently reused.
- If multiple IDE windows can heartbeat the same worktree, decide whether that is one lease or reference-counted leases.
- If you use `curl --unix-socket`, choose a socket path without spaces and verify the minimum curl version in your target environments.

- Use `realpath(repoRoot)` before hashing, or symlinks will create duplicate daemon identities.
- Keep socket paths short; macOS Unix socket paths are tighter than Linux.
- On startup, if the socket path already exists, try connecting before unlinking it; only remove it when it is stale.
- Put sockets/state under a user-owned runtime dir with `0700` permissions.
- If you keep any TCP endpoint, bind to `127.0.0.1` explicitly, not `0.0.0.0`.
- If you use a state file, never trust it without PID liveness plus daemon identity validation.
- Handle concurrent `pick-repo.ts` invocations for the same repo so only one daemon wins.
- If the repo is moved on disk, the old daemon identity should not be silently reused.
- If multiple IDE windows can heartbeat the same worktree, decide whether that is one lease or reference-counted leases.
- If you use `curl --unix-socket`, choose a socket path without spaces and verify the minimum curl version in your target environments.
