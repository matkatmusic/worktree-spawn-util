### Code Review Findings

**1. Command injection in `tmux new-session` shell evaluation**
- **Severity**: Critical
- **File and line**: `src/cli/pick-repo.ts`, line 104 (`const daemonCmd = ...`)
- **What**: The unsanitized `selection.repoRoot` path is directly interpolated into `daemonCmd`, which is then passed as a single string argument for `tmux new-session` to execute.
- **Why**: `tmux` passes this string to `/bin/sh -c` for execution. If a repository path contains shell metacharacters or quotes (e.g. `"; rm -rf /; echo "`), it will result in arbitrary shell command execution.
- **Fix**: Use explicit arguments instead of relying on shell evaluation. Pass the command array to tmux securely, e.g.:
  `await execFileAsync("tmux", ["new-session", "-d", "-s", sessionName, "node", daemonPath, selection.repoRoot]);`

**2. Invalid tmux session names and duplicated logic**
- **Severity**: High
- **File and line**: `src/cli/pick-repo.ts`, line 103 and `src/ide/index.ts`, line 156
- **What**: The tmux session name is constructed inline as `${basename(repoRoot)}_daemon` in two distinct places. Furthermore, it does not sanitize periods (`.`), colons (`:`), or spaces, and is left unquoted in the IDE task.
- **Why**: `tmux` strictly rejects session names containing periods or colons. If the repo root is named e.g. `my.repo`, `tmux new-session` will fail and the CLI will silently fall back to a detached background spawn. However, VS Code will still generate a `Daemon Monitor` task looking for that invalid session name, breaking the `--visible` mode functionality. If the repo name has spaces, `tmux attach -t My Repo_daemon` will also fail.
- **Fix**: Extract a shared helper function (e.g., `getDaemonSessionName(repoRoot)`) that sanitizes invalid characters (`.replace(/[\.: ]/g, '_')`). Ensure it is reused in both files and that the IDE shell command quotes the session name appropriately: `command: \`tmux attach -t "\${sessionName}"\``.

**3. Shared log file write contention**
- **Severity**: Medium
- **File and line**: `src/cli/daemon.ts`, line 30 and `src/cli/heartbeat.ts`, line 23
- **What**: The `daemon.log` is written directly into `getSocketDir()` without being namespaced by repository.
- **Why**: `getSocketDir()` provides a shared directory for the user (e.g., `/tmp/wtsu-501`). If you have daemons and VS Code instances running for multiple distinct repositories concurrently, they will all interleave their unsynchronized logs into the exact same `daemon.log` file, making debugging near impossible.
- **Fix**: Scope the log file per repository. For instance, tie it to the socket path (`const logFile = \`${socketPath}.log\``), or write the log directly into the repository's `.vscode/` directory.

**4. Silent continuation upon socket initialization timeout**
- **Severity**: Low
- **File and line**: `src/cli/pick-repo.ts`, line 125
- **What**: The `pick-repo` script polls for up to 5 seconds waiting for `isSocketAlive(socketPath)`. If the daemon fails to start within the window, the loop exits and the script proceeds without acknowledging the failure.
- **Why**: If the daemon immediately crashes due to a runtime error or port binding failure, the user is left with no indication that their daemon isn't running until automated cleanup mysteriously fails to trigger later.
- **Fix**: Add a check after the polling loop exits to warn the user if it failed:
  `if (!await isSocketAlive(socketPath)) console.warn("[pick-repo] Warning: Daemon failed to start.");`

**5. Synchronous I/O in Node.js event loops**
- **Severity**: Low
- **File and line**: `src/daemon/server.ts`, line 54 and `src/heartbeat/client.ts`, line 38
- **What**: Using `appendFileSync` to write to the log file on every heartbeat dispatch/receipt.
- **Why**: Synchronous I/O blocks the Node event loop. While heartbeat traffic is relatively low (one message every 5 seconds per worktree), it is an anti-pattern for asynchronous network servers and clients, limiting concurrency unnecessarily.
- **Fix**: Switch to asynchronous file writing using `fs.promises.appendFile()`, or instantiate a writable stream at startup and call `stream.write()`.

**6. Blocking interactive prompt**
- **Severity**: Nit
- **File and line**: `RunMeFirst.sh`, line 48

- **Fix**: Check if the shell is interactive (`if [ -t 0 ]; then`) before prompting, or provide an automatic `-y` execution flag.
