================================================================================
CRITICAL — Must fix before merging
================================================================================

1. No test for ignorable-only changes (.claude/ or .vscode/)
   Flagged by: [G] [C] [S] [O] — unanimous
   The onlyIgnorableChanges() function is the gatekeeper for the entire cleanup
   decision tree. Zero test coverage for the "only .claude/ changes present"
   path means a regression (e.g., a prefix check matching ".clauderc") would be
   invisible.
   FIX: Add a test that writes a file at .claude/settings.json inside the
   worktree, then verify the daemon DELETES (treats changes as ignorable).

2. waitForOutput() can miss patterns split across chunks
   Flagged by: [S] [O] — moderate (but both infrastructure-focused reviewers)
   stdout chunks are not guaranteed to align to message boundaries. If
   "cleanup" arrives as "cle"+"anup" in two chunks, includes() on each chunk
   individually will never match. Unlikely with short messages but non-zero.
   FIX: Buffer all stdout into a growing string and re-check the full buffer
   on each data event, instead of checking each chunk in isolation.

================================================================================
HIGH — Should fix
================================================================================

3. No test for mixed changes (ignorable + non-ignorable)
   Flagged by: [G] [S] [O] — strong consensus
   A worktree with both .claude/ changes AND a real user file should PRESERVE.
   The every() logic handles this, but no test proves it.
   FIX: Add a test with .claude/foo + real-file.txt, assert PRESERVE.

4. No test for staged-but-not-committed changes
   Flagged by: [G] [S] [O] — strong consensus
   Test 2 only covers untracked files. A git-added-but-not-committed file has
   a different status --porcelain code ("A " vs "??"). The parsing should
   handle it, but there is no proof.
   FIX: Add a test that stages a file with git add, assert PRESERVE.

5. afterEach uses magic sleep instead of waiting for process exit
   Flagged by: [G] [S] [O] — strong consensus
   Line 217: 500ms setTimeout after killing daemon. On slow CI, daemon may not
   release socket in time, causing the next test to encounter a stale socket.
   FIX: Replace with `await new Promise(r => daemonProc.on('exit', r))`.

6. Tests run against stale dist/ if not rebuilt
   Flagged by: [C] [S] [O] — strong consensus
   Lines 22-23 reference dist/cli/daemon.js and dist/cli/heartbeat.js. No
   freshness guard. Vitest does not rebuild before running.
   FIX: Either add a beforeAll that runs `npm run build`, use tsx to run
   TypeScript source directly, or add a vitest globalSetup that builds first.

7. waitForOutput "cleanup" rejection is silently swallowed
   Flagged by: [G] [S] [O] — strong consensus
   Lines 350-355: try/catch around waitForOutput(daemonProc, "cleanup", 10000)
   logs the error but does not fail the test. If cleanup never triggers, test
   silently proceeds to assertions which may be non-deterministic.
   FIX: Remove the try/catch, or re-throw the error so the test fails loudly
   with a clear "cleanup never triggered" message.

8. Replace 1s sleep after cleanup detection with deterministic wait
   Flagged by: [G] [O] — moderate
   Line 374: arbitrary 1000ms sleep waiting for git operations to complete.
   Classic CI flakiness source.
   FIX: Wait for the daemon's final decision message ("Removed worktree and
   branch" or "preserving" or "uncommitted changes") instead of sleeping.
   Alternatively, poll for directory/branch deletion up to a timeout.

MEDIUM — Should fix when touching this code
================================================================================

9. Missing negative assertions on DELETE tests
   Flagged by: [O] — solo, but well-reasoned
   Tests 1 and 4 assert the worktree was deleted but do NOT assert the daemon
   did not log "preserving" or "uncommitted changes". A bug where the daemon
   first logs "preserving" then deletes anyway would pass.
   FIX: Add expect(output).not.toContain("preserving") to DELETE tests.

10. Weak "merged" substring match in Test 4
    Flagged by: [O] — solo, but clearly correct
    Line 497: expect(output).toContain("merged") would also match "unmerged
    commits" (the opposite case). A bug printing "unmerged" would pass.
    FIX: Use expect(output).toContain('is merged into') to match the actual
    daemon log message exactly.

11. waitForOutput leaks listeners
    Flagged by: [S] [O] — moderate
    Each call registers a data listener that is never removed. After resolution,
    old listeners remain attached with stale closures. Not a correctness bug
    in current usage but will cause node warnings if many calls are made.
    FIX: Return a cleanup function or remove the listener after resolve/reject.

12. Fast-forward merge path not tested
    Flagged by: [G] [S] — moderate
    Test 4 uses --no-ff. A FF merge leaves the branch tip as a direct ancestor.
    git branch --merged handles this, but without a test there is no proof.
    FIX: Add a test that merges without --no-ff, assert DELETE.

13. Multiple commits on branch not tested
    Flagged by: [S] — solo
    All tests use at most one commit. Real worktrees will have multiple.
    FIX: Add a test with 2+ commits, verify merge detection still works.

14. No test for "no parent info" legacy fallback path
    Flagged by: [S] [O] — moderate
    daemon-server.ts lines 97-109 have a fallback when parentBranch/parentCommit
    are missing. No test coverage for this safety-critical path.
    FIX: Register a worktree without parent info, verify cleanup still works.

15. Timing dependency on heartbeat seq number "#3"
    Flagged by: [S] — solo (Sonnet rated Critical, but others did not flag)
    Line 340: waitForOutput for "Received heartbeat #3" is brittle if the
    numbering scheme changes. Works today but has no compile-time safety.
    FIX: Wait for a count-agnostic pattern like "Received heartbeat" appearing
    3 times, or extract the magic number into a constant.

16. "cleanup" substring match is fragile
    Flagged by: [G] [O] — moderate
    waitForOutput waits for "cleanup" but the actual message is "evaluating
    cleanup". If wording changes to "clean-up" this breaks silently.
    FIX: Use the more specific pattern "evaluating cleanup".

17. Fixed 200ms sleep after register (line 378)
    Flagged by: [S] — solo
    Heuristic timing; could fail on slow systems.
    FIX: Wait for a daemon acknowledgment message instead.

18. Git lock file risk in afterEach
    Flagged by: [G] — solo
    If daemon was mid-git-operation when killed, index.lock could be left
    behind, causing teardown to throw.
    FIX: Add a retry or delete index.lock before git worktree remove.

================================================================================
DISAGREEMENTS
================================================================================

A. Socket path collision risk
   Sonnet flagged [High] that getSocketPath() could theoretically hash two
   different tempdir paths to the same value. Codex, Gemini, and Opus all noted
   that per-test temp dirs make socket isolation sound. Gemini explicitly called
   it "a good design choice." VERDICT: Low risk. Verify getSocketPath uses the
   full path, not a truncated hash. No test needed unless hash collisions are
   plausible.

B. Heartbeat seq "#3" timing dependency severity
   Sonnet rated this Critical. No other reviewer flagged it at all. The pattern
   works reliably because heartbeats are sequential and chunks containing "#3"
   will always include the substring. VERDICT: Medium at most. Worth making
   more robust, but not blocking.

C. afterEach correctness for heartbeat cleanup
   Opus initially flagged heartbeatProc being set to null before process exit
   as potentially dangerous, then self-corrected after re-reading the code:
   afterEach correctly handles the error path because heartbeatProc is only
   nulled after kill(). VERDICT: No bug. Current code is correct.

D. Overall test quality assessment
   All four reviewers agree the E2E approach is sound and the four core
   scenarios are correctly tested. The disagreement is on severity of gaps:
   Gemini and Codex are more lenient (tests are "reasonable"), while Sonnet
   and Opus identify more granular issues. All agree the ignorable-changes
   gap is the highest-priority missing test.
