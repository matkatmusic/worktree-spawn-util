#1  Command injection / shell-unsafe repo names in tmux + VS Code tasks
    Severity: Critical (Gemini, Claude) / High (Codex)
    Files: src/cli/pick-repo.ts:104, src/ide/index.ts:156, src/ide/index.ts:107,129
    Flagged by: ALL THREE REVIEWERS
    What: basename(repoRoot) is interpolated directly into shell command
          strings for tmux session names and VS Code task commands. Repo
          paths containing shell metacharacters (spaces, semicolons, $, etc.)
          can cause command injection or broken tmux sessions.
    Why:  Arbitrary shell execution from a maliciously named directory. Even
          benign names with periods/colons break tmux (it rejects those chars
          in session names). Two repos with the same basename collide.
    Fix:  Create a shared getDaemonSessionName(repoRoot) helper that:
          (a) derives from a stable hash (matching socket path strategy),
          (b) sanitizes invalid chars (.replace(/[\.:$ ;&|`()]/g, '_')),
          (c) is used in both pick-repo.ts and ide/index.ts.
          For VS Code tasks, use the args array format instead of inlining
          into command strings, or properly quote all interpolated values.

#2  Shared log file (daemon.log) — all repos write to same file
    Severity: High (Claude) / Low (Codex, Gemini — as Medium)
    Files: src/cli/daemon.ts:30, src/cli/heartbeat.ts:23
    Flagged by: ALL THREE REVIEWERS
    What: Both daemon and heartbeat processes compute
          join(getSocketDir(), "daemon.log") and write with appendFileSync.
          Multiple repos running concurrently interleave their logs into
          one file.
    Why:  Breaks the per-repo isolation the socket design established. Makes
          debugging race conditions or cleanup failures nearly impossible.
    Fix:  Scope log file per repository: const logFile = `${socketPath}.log`
          or derive from the same repo hash as the socket.

#3  tmux session name duplication — logic repeated in two files
    Severity: High (Gemini, Claude) / High (Codex — combined with #1)
    Files: src/cli/pick-repo.ts:103, src/ide/index.ts:156
    Flagged by: ALL THREE REVIEWERS
    What: Session name `${basename(repoRoot)}_daemon` is constructed inline
          in two separate locations with no shared helper. No sanitization
          of periods, colons, or spaces.
    Why:  tmux rejects names with periods/colons. Duplicate basenames across
          repos collide. The monitor task may attach to the wrong daemon.
    Fix:  Extract to a shared getDaemonSessionName(repoRoot) utility.
          (This is the same fix as #1 — they are related.)

#4  Non-null assertion on optional repoRoot when visible=true
    Severity: High (Claude) / Low (Codex)
    Files: src/ide/index.ts:201-202, src/ide/index.ts:222-223
    Flagged by: Claude, Codex
    What: repoRoot! is used with a non-null assertion but repoRoot is typed
          as optional. Calling writeWorktreeTasksFile(path, name, undefined,
          true) would produce a task referencing "undefined_daemon".
    Why:  Silent malfunction — runtime crash or nonsensical task definition.
    Fix:  Either make repoRoot required when visible=true (enforce via types
          or runtime check), or guard with if (visible && repoRoot).

#5  Silent continuation after socket poll timeout
    Severity: Medium (Claude, Codex)
    Files: src/cli/pick-repo.ts:119-127
    Flagged by: Claude, Codex
    What: The poll loop waits up to 5s for the daemon socket. If it never
          comes alive, execution continues silently — writing tasks and
          opening the IDE as if the daemon were healthy.
    Why:  Daemon startup failures become invisible. User assumes automatic
          cleanup is active when it is not.
    Fix:  After the loop, check isSocketAlive one final time. If still dead,
          log a hard warning or exit non-zero. At minimum:
          console.warn("[pick-repo] WARNING: Daemon socket not ready after 5s")

#6  Missing semicolon on logToFile call
    Severity: Nit (Claude, Gemini)
    Files: src/daemon/server.ts:121-122
    Flagged by: Claude, Gemini
    What: logToFile(...) call missing trailing semicolon. ASI handles it but
          it is inconsistent with the rest of the codebase.
    Fix:  Add the semicolon.

--- MEDIUM ---

#7  Synchronous I/O (appendFileSync) in event loops
    Severity: Low (Gemini) / Medium-implied (Claude — via log contention)
    Files: src/daemon/server.ts:54, src/heartbeat/client.ts:38
    Flagged by: Claude, Gemini
    What: appendFileSync blocks the Node event loop on every heartbeat.
    Why:  Anti-pattern for async network servers. Low impact at current
          traffic (5s intervals) but limits concurrency.
    Fix:  Switch to fs.promises.appendFile() or use a writable stream.

#8  Race condition: async cleanup during Map iteration
    Severity: Critical (Claude)
    File: src/daemon/server.ts:151-155
    What: for...of iterates heartbeats Map and calls async cleanupWorktree()
          which deletes from the Map. cleanupWorktree is not awaited, so
          multiple async cleanups can overlap. Next interval tick can fire
          while cleanups are in flight, potentially triggering duplicate
          git worktree remove --force and tmux kill-session calls.
    Why:  Double cleanup of same worktree, or removing a worktree that was
          re-registered between check and completion.
    Fix:  Collect expired worktrees into an array first, delete from map
          immediately, then run cleanups. Or add a cleaningUp: Set<string>
          guard to skip worktrees already being cleaned.
    Note: Neither Codex nor Gemini flagged this. The ES2015+ spec does
          guarantee safe deletion during Map iteration, but the async
          concurrency concern is distinct from the iteration safety question.

#9  Heartbeat worktree name not quoted in task command
    Severity: High (Claude)
    File: src/ide/index.ts:129
    What: --worktree ${worktreeName} lacks quotes in the command string,
          while --repo-root "${repoRoot}" is quoted.
    Why:  Worktree names with spaces would break the command.
    Fix:  Quote it: --worktree "${worktreeName}"

#10 Session header format inconsistent with logToFile format
    Severity: Medium (Claude)
    File: src/daemon/server.ts:62-70
    What: The session header block does not use the logToFile() helper and
          has a different format (no [timestamp] prefix).
    Fix:  Use logToFile() for the header lines, or accept the format
          difference as intentional for readability.

#11 Log file grows without bound
    Severity: Medium (Claude)
    File: src/daemon/server.ts:53-54
    What: appendFileSync with no rotation. At 5s heartbeat intervals, log

    Fix:  Implement simple size-based rotation or document that logs are in
          /tmp and cleared on reboot.

#12 reloadIdeWindow is exported but no longer called

#13 heartbeatCount module-level mutable state

#14 Fallback spawn doesn't pass --silent flag

SECTION 3: DISAGREEMENTS

No direct contradictions were found between reviewers. The main variance is
in severity calibration:

1. Command injection: Gemini and Claude rated Critical; Codex rated High.

   realistic scenario for this tool.

   Codex and Gemini did not identify it. The concern is valid (unawaited
   async functions during iteration can cause duplicate cleanups) but
   requires specific timing conditions to manifest.

   Claude focused on the silent malfunction; Codex focused on the API
   type signature mismatch.
